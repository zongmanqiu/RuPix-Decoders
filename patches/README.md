# 第三方补丁登记（`patches/`）

本目录登记**对仓库外第三方源码所做的补丁**——被补的源码本身不进仓库（放在工作区
`../.3rd/<name>-<version>/`，见那里的 `README.md`），进仓库的是**能重建它的最小材料**：
一份对上游原文的补丁 + 一份人读说明 + 一份机器读的登记。

| 目录 | 上游 | 版本 | 补丁用在 | 补丁 |
|---|---|---|---|---|
| `emfsdk-0.2.0/` | `KaiserY/emfsdk`（crates.io `emfsdk`） | 0.2.0 | `doc` 档的 `doc-emf`（EMF/EMZ 文本） | E01 / E02 |

## 每个目录必须有什么

| 文件 | 作用 | 谁读 |
|---|---|---|
| `manifest.json` | 基线版本 / 补丁清单（编号、日期、说明、触及路径）/ 上游核对日期 | `tools/check_patches.py`（构建门禁） |
| `README.md` | 为什么改、改了哪里、怎么重放、上游怎么核对 | 人 |
| `*.patch` | 对**上游原文**的统一 diff（`a/` `b/` 前缀，可 `git apply`） | 重放补丁的人 / 门禁核路径 |

判定标准只有一条：**上游原文 + 本目录全部补丁 = 构建时用的那份副本**。
门禁不去比字节指纹（理由见下一节），它核三件可离线核的事：补丁是 LF 行尾、补丁里
`diff --git` 触及的路径与 `manifest.json` 的 `files` 一一对应、副本里被补的那些文件都在。

## 这里不记哈希（2026-11-02 用户口径）

补丁由本仓作者写、副本由本仓作者放到 `.3rd`、release 也只有作者能发——指纹要挡的
"第三方篡改"根本不存在，而成本是实打实的：`rustfmt` 一次重排、换一次工具链就换字节，
于是"登记一串十六进制"变成每次动代码都要重算、算错就误报门禁红（2026-11-02 就为这个
白查过一轮 emfsdk 副本）。

**识别一份补丁只认 `crate + version + 补丁编号 + 触及路径`。**
2026-11-02 删掉的登记字段：`crate_sha256`、`upstream_sha256`、`patched_sha256`、`patched_blob`。
`files` 同时从"对象数组"简化成"路径字符串数组"——路径是事实，摘要是维护负担。

## 这是「跟随上游」的补丁，不是分叉

- **基线永远取上游的同一个版本**：补丁只叠加在 `emfsdk 0.2.0` 原文上，不携带任何上游
  之外的改动；上游一旦升级，我们重放补丁，而不是把旧文件整份搬过去。
- **每 90 天必须去上游核对一次**：`manifest.json` 的 `upstream_check.checked_at` 过期后
  `tools/check_patches.py` 直接判红，构建流水线停下——核对完（无论上游有没有变）把日期改成
  核对当天。这条是刻意的：「上游发了新版我们不知道」不会显形，只能靠日期逼一次人工动作。
- **升级流程写在各目录 README 的「上游核对 / 升级」一节**，与工作区 `.3rd` 的 `SOURCE.md`
  保持同一份事实（两处都改，不许只改一处）。
